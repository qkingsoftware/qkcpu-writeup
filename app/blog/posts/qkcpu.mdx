## The designing process

### First steps

I have installed all tools, such as the oss-cad-suite to start writing the actual verilog code.
Verilog is one of the HDL's (Hardware Description Language) that exist, a language that can synthesize to actual patterns on the wafer (or logic for FPGA)
I cloned the [template repository](https://github.com/TinyTapeout/ttgf-verilog-template) and started looking into it.
I also looked at some existing repositories build around this template to understand better how it works.

I quickly realised that just starting directly wasn't a good idea, I needed a plan first.
I decided that it was a good idea to make each component iduvidually first and later connect them.
In practice this shifted a bit, but more on that later.
I made a little list of what components I needed and what they had to do.

- **ALU:** Do math and other operations with binary
- **Registers:** Small 8-bit registers I can use in ALU operations
- **Data RAM:** Space to store and load data produced by the CPU
- **Program RAM:** Storage for the actual program that the CPU executes
- **Decoder:** Decodes my instructions to be actually usable
- **Program Counter:** Remembers the memory address of instruction it's executing

I wanted the RAM to be asynchronous read and synchronous write.
Later this all updated.

### ALU

The ALU, personally I thought the unit that will be doing every calculation was hard to make.
I was wrong in that, verilog has thought about this, it's pretty easy.
In case of the ALU and it's simplicity, this will be one of the few time that I will fully explain the verilog code.
In verilog you can add 2 values like this:
```verilog
result = a + b;
```
This is an actual snippet from my ALU.
It adds a to b and stores the result in result.
Verilog has a lot of those operations that can be done that easily.
```verilog
// Comment to fix syntax highlighting on the writeup. Dont mind this.
`default_nettype none

module alu (
    input wire [7:0] a,
    input wire [7:0] b,
    input wire [3:0] opcode,
    output reg [7:0] result
);

    always @(*) begin
        case (opcode)
            4'b0000: result = a + b; // ADD
            4'b0001: result = a - b; // SUB
            4'b0010: result = a & b; // AND
            4'b0011: result = a | b; // OR
            4'b0100: result = a ^ b; // XOR
            4'b0101: result = ~a; // NOT
            4'b0110: result = a << 1; // SHL
            4'b0111: result = a >> 1; // SHR
            default: result = 8'b00000000; // Default is add, for if you forget to set the opcode
        endcase
    end

endmodule

`default_nettype wire
```

This is the full ALU, the ALU receives a and b and an opcode.
I went with 4-bit opcodes, so 16 total opcodes.
With `` `default_nettype none `` I say to the compiler, that it should give an error if I use a signal that doesnt exist.
This was useful to catch small typing errors or whole signals I forgot.

In the module block I define (a module is a component that I can later use in another verilog file) that we have 2 8-bit inputs named a and b.
Figuring out what the difference between registers and wires was took me a while.
[7:0] In verilog means that I define that variable a is 8-bits total, which I want since we are making an 8-bit cpu.
Inside the always block I have put a case statement. That means when the opcode is for example 0001 it performs an ADD operation.
I have added basic operations that I might need to this list. 
I added a default statement as well for the cases that no opcode is given. I wasn't sure what would happen so I added it for safety.
with `` `default_nettype wire `` I undo the operation set with the default_nettype none.

I also wrote a simple testbench for this in verilog. It just performs each opcode on some values and it checks if the results are equal to the expected ones.

### Register

I started with one register, I honestly dont remember why I didn't add more when I started. 
A register is basically a small space to store data. In my case a register is 1 byte (8 bits). It can hold a single value.
That doesn't seem like a lot and it isn't, but it's used directly in processing. All the other data is stored in the ram later on.
Basically when the enable flag is true it stores a value. When enable is false it keeps it.
The rst_n signal is meant to reset that register, when its true it wipes it to zero. When its false everything operates normally.
My testbench for this confirmed this logic.

### Program Counter

My program counter is the way to tell at what instruction you are in the program memory.
Mine is 6-bits wide, so I can hold a total of 64 instructions.
It's not a lot, but since this is a proof of concept I will go for it.
(And I should be able to reflash and store to dataram....)

I have made a simple visual to explain it better alongside the first version of my program counter in verilog.

![Program Counter](/images/qkcpu/counter.png)


```verilog
module pgrm_counter(
    input wire clk,
    input wire rst_n,
    input wire enable,
    input wire [0:0] jump,
    input wire [5:0] jump_address,
    output reg [5:0] count
);

    always @(posedge clk)
        if (!rst_n) begin
            count <= 6'd0;
        end else if (jump) begin
            count <= jump_address;
        end else if (enable) begin
            count <= count + 6'd1;
        end
endmodule
```

The program counter also has a jump option for if we want to jump further or earlier into the program memory to create loops.
It resets when the rst_n is true just as the other modules.

### RAM (Program and Data) v1

RAM, Random Acces Memory. The hardest part of this journey. I went with 128 bytes of dataram and another 128 bytes for program ram.
Why would you use RAM for programs you might ask. If I hardcode the program or use ROM I am not able to change what the cpu does when its on silicon.
My first attempt on RAM was terrible. I went with asynchronous read and synchronous write RAM. Bad idea I got told by some more experienced developers in the community.
The code here underneath is is the first iteration of my RAM. @(*) lets it read on any moment (asynchronous) and the @(posedge clk) means that I can only read on a positive cycle of the clock (synchronous).

```verilog
module dataram (
    input wire clk,
    input wire [5:0] address,
    input wire [7:0] data_in,
    input wire write_enable,
    output reg [7:0] data_out
);

reg [7:0] memory [0:63];
    always @(*) begin
        data_out = memory[address];
    end
    always @(posedge clk) begin
        if (write_enable) begin
            memory[address] <= data_in;
        end
    end
    endmodule
```

This was the most basic RAM ever and it was far from optimised. I will come back on this later.

### GPIO

I have came to a conclusion. I have used all the 8 output pins for debugging and the 8 bidirectional pins for outputs.
This is a bit of a waste, since we have so few of them and all are used.

I have revamped the way those pins are used.
Output pins are now actually the output, instead of just debug pins.
The input pins remain inputs.
For the bidirectional pins I did something else.
When load program is enabled they are used to upload the program to the program RAM.
When it's disabled they can be assigned by the MMIO as inputs and outputs.
This is a giant change and it took me a while. 
But GPIO is now also completed (first checklist).

MMIO stands for Memory Mapped Input & Output
addresses 0x60–0x67 are used to set the mode of the pin.
If the pin was an input and you read from it it returns the result.
If you read 0x78 you get the raw value of the pins, an 8-bit addres with the value of each pin.


### PWM

As extension on the GPIO there is PWM.
You can set it using the existing MMIO.
Addresses 0x70–0x77 are used for setting the duty value of the PWM pin (if set to use PWM)
Adress 0x79 is used to set the PWM Period.
If you don't know what PWM is and how it works I recommend you checking [PWM Wikipedia](https://en.wikipedia.org/wiki/Pulse-width_modulation)
